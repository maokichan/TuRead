# 决策：种子机制 = 开发期便利；官方插件必须可卸载

Status: implemented

## Problem

v0.2.1 落地插件系统时，「问」随包首发，为开发方便实现了 seeder「缺则种」（首发资源自动补齐
运行时目录）。执行层从此推导出一项**从未被裁定的产品策略**：「官方种子件拒删，不可卸载」
——写进了代码注释、设置页（种子件不显示卸載按钮 + 「官方隨附，不可卸載」标注）、子树红线。
用户 2026-11-10 明确否决：「我没有下过任何关于官方插件不可以删除的说法，这是错误的执行」。
偏差本质：**开发便利被 dressed up 成产品豁免**，且代码注释以「将来如需可卸种子件，先给
seeder 加 opt-out」的口吻把越权固化为设计意图——有再次被后续 agent 当作既定规则捡回的风险。

## Decision

- **官方插件可卸载**（用户裁定）：卸载种子件 = 删运行时目录 + 记入 opt-out 清单
  （settings `plugin-seeder:opt-out`，主进程独占写），之后的 `seed()` 跳过这些 id——
  「缺则种」不再复活用户的卸载决定。
- **种子机制本体保留**：定位 = **开发期便利 + 首发自动补齐**，不是卸载豁免的依据；
  `seeded` 字段降级为纯元数据（设置页「官方隨附」提示）。
- 设置页：卸載按钮对全部插件可见；种子标注改为「（官方隨附）」。
  ⚠ **后续演进（同日第三轮裁定，见 plugin-lifecycle）**：首发自动补齐机制整体废除（官方
  插件 = 手动安装）——本笔记的 opt-out 清单与「种子机制本体保留」已随之退役，卸载不存在
  「复活」问题；本笔记留下的常驻价值 = Alternatives 里的纪律教训。

## Alternatives considered

- **维持拒删 + 只加「停用」**：输在——停用解决「不想用」，解决不了「不想看见它在这台机器上」；
  且拒删理由（复活）是实现缺陷而非产品价值，缺陷不能反过来正当化限制。
- **彻底废除 seeder**：输在——首发自动补齐（新装机/换机「問」开箱即用）仍是被需要的行为；
  该废的是「种入无视卸载意愿」，不是种入本身。目标形态（要不要市场、主动安装、恢复通道）
  归插件生命周期总纲（TODO），不在本裁定范围。
  （注：同日晚些时候用户第三轮裁定废除了整个自动补齐机制，见 plugin-lifecycle——本条
  「输在」的理由被推翻，保留作决策链记录。）

## Consequences

- 所得：卸载语义对所有插件一致；「官方特权」语义从产品中移除。
- 代价：⚠ **主动安装/恢复通道尚未存在**——种子件卸载后「問」暂无重装路径（重装 = 手动把
  插件文件夹放回运行时目录 + 清 opt-out 键）。这是生命周期总纲②（安装流程缺失）的既知
  缺口，不因本裁定扩大，但由它显形。
  （已解决：同日插件生命周期批落地 zip 安装管道，重装 = 重新导入，见 plugin-lifecycle。）
- 纪律教训：**开发便利不得自我升格为产品规则**——实现里发现的「必要限制」必须回到用户
  裁定，而不是在代码注释里代拟将来时政策。
