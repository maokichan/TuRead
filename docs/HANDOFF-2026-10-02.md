## 2. 困境：四个具体病灶

### 病灶一：开发节奏混乱

表现不是"进度慢"，是**产出与项目推进脱钩**：
- 讨论进行了多轮，仓库里留下的东西是一份分析文件（且事后未存）。

  **判别方法只有一个：这次会话在仓库里留下了什么可提交的东西。**

### 病灶二：技术细节泄露

讨论交互问题时，实现词汇持续涌入并**冒充结论**：
- "iframe 焦点盲区""canvas 重开""store 接线""display:none 状态继承"——
  这些换掉技术栈就不成立，属于实现泄漏，按本项目自己的判据（换栈仍成立？）**根本不该进入交互讨论**。
- 后果：讨论在实现可能性与交互意图之间来回滑，两边都不落地。

## 3. 为什么"交互任务的自然模型"这次没能帮上忙

不是方向错了，是**它与当前项目状况不匹配**。背景见 `../自然模型/`（研究笔记，非程序项目）。

- **对个人有启发**：把"交互决策"拆成"任务决定的"与"取向可选的"，确实厘清了看问题的方式；
  "收敛"可以当作可判来源、"强度"可以当过滤器，这些是有用的思考方向。
- **对项目帮助不大**，原因有三：
  1. **它产出的是描述层，不是动线。** 分类法需要人主动去读才生效；
     能真正起作用的纪律长这样——`client/docs/STYLE.md` §5.9 规定"动渲染层代码前先回这里看"。
     **一个规定在某个动作之前必须被查阅的东西才有约束力，读物没有。**
  2. **它解决的是元问题，而项目缺的是具体功能。** 在 PDF 翻页都还不符合预期的时候，
     给交互层建模型，等于给还没修好的路规划交通规则。
  3. **它容易变成新的负担。** 每多一份描述，就多一份要读、要认、要判断的东西——
     这正是本次要治的病。

**结论**：这个方向**挂起，不是否定**。重启条件写在这里——
**当交互层的问题已经多到"每次都要重新发明判断标准"成为实际瓶颈时**，再回来。
现在不是。

1. **PDF 滚动卡手**：kookit `PdfRender` 渲染调度改造 —— 滚动回调挂 `requestIdleCallback`；
   预渲染 3 页从"并发抢主线程"改为**串行后台队列**（`pdfPrefetchChain` + 代次令牌）。
2. **暗色逐像素烘焙**：`bakeDarkModePixels` 每页渲染完成时对主画布逐像素复算原 CSS filter
   的精确数学（invert → hue-rotate(180) 矩阵 → contrast），取代挂在图层上的实时 filter。
   ⚠ 首版用"HSL 亮度反转保留色相"近似，彩色像素与 filter 有可见偏差（用户报"色彩更正错误"），
   **已改精确复算**——教训：近似 filter 的色彩口径要逐位对拍，不要凭直觉造近似。
3. **PDF 专属纸宽档位**：`readerWidthPdf`（默认 1080 / 档 840·1080·1320），开书**前**按格式切
   `--read-width`（PDF canvas 按渲染时刻容器宽定像素，晚切一帧就按旧宽画）；仍给挂件让位。
4. **滚动模式页卡边缘**：适配器注入 `.pdf-container{border:1px solid --page-edge}`（先注入后量高）。
5. **口径修正**：「阅读模型选型未定」是没看源码写出来的——滚动早已存在（且是默认值），问题是卡手。
   本文件 §0/§4 与 TODO 已改。**页眉页脚不裁**（用户定，远期候选 = kookit `pdfCrop` + 每书记忆）。

**本轮发现、已登记 TODO、尚未修（下一步优先）**
- **烘焙渲染竞态**：当前页"立即通道"与预渲染"后台队列"可对同一页并发 → 已烘焙 canvas 被未烘焙的
